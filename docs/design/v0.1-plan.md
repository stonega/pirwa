# Pirwa v0.1 plan

## Implementation status — 2026-11-15

M1–M3 functionality is implemented and has deterministic and isolated real-KVM
coverage. M0 now has a native GTK 4 SPICE console and synthetic inventory/display
baselines. M4 has CI, metadata, gettext infrastructure, and an RPM recipe.
The full acceptance gates are still open; this is not a 0.1.0 release.
See [implementation validation](../research/v0.1-validation.md) and the
[console decision](console-decision.md) for evidence and limits.

## Product outcome

A GNOME desktop user can discover local VMs, create a Linux VM from a local ISO,
install and use it through a console, control its power, change basic resources
while stopped, and remove it safely. Keep the short, approachable workflow of
Boxes. Prioritize responsiveness, idle cost, and guest execution over feature
count. This is a new application, not a Boxes fork.

## Release scope

| Area | v0.1 behavior |
| --- | --- |
| Host | Linux x86_64 with KVM; Fedora is the initial validation platform |
| Connections | `qemu:///session` default; explicitly selected `qemu:///system`; one active connection |
| Collection | Names, states, search, incremental updates, useful empty/error states |
| Boxes onboarding | Prompt only for installed stable Boxes Flatpak; import a stopped supported guest into Session with a copied disk/firmware, progress and rollback; native Boxes VMs appear automatically |
| Power | Start, graceful shutdown, restart, pause/resume; force stop requires explicit confirmation |
| Creation | Local bootable Linux ISO, name, CPU, RAM, disk size, visible progress and rollback |
| Windows guests | Experimental x86_64 Windows 10/11 ISO profiles with user-supplied VirtIO driver media; Windows 11 requires UEFI, Secure Boot and TPM 2.0; real installation acceptance remains open |
| Storage | App-created qcow2 volume in a selected writable libvirt pool |
| Guest defaults | KVM, capability-checked host CPU, virtio devices, supported UEFI, available userspace networking |
| Proxy networking | Automatic manual-host-proxy routing for supported Session VMs at Start; IPv4 TCP and DNS, with no guest proxy setup |
| Existing VMs | Discover in place without changing XML; import one standalone qcow2 image by copying into an owned volume |
| Console | Working keyboard, mouse, resize/fullscreen; embedded only after M0 passes; supported external viewer otherwise |
| Settings | Rename, CPU and RAM while powered off; ISO eject after install |
| Removal | Remove definition; offer disk deletion only for verified app-owned volumes |
| Integration | Desktop launcher, icon, keyboard access, gettext infrastructure, light/dark and accessibility checks |
| Distribution | One amd64 DEB, Fedora x86_64 RPM and GNOME-runtime Flatpak attached to GitHub Releases; the same source RPM rebuilt through copr-cli |

Existing qcow2 images with backing chains and unsupported formats must get a
clear rejection in v0.1. Do not modify a user's original image. System mode needs
permission checks; connecting must not automatically create a host-wide network.
Choose available userspace networking from capabilities for session guests.

Snapshots, cloning, unattended installation, ISO downloads, Windows Server/older Windows profiles,
USB/GPU passthrough, shared folders, remote hosts, live/remote migration, multi-monitor,
and background autostart management are deferred.

The 2026-11-16 release requirement adds DEB and Flatpak distribution to M4.
The Flatpak connects to host libvirt and uses host QEMU; it does not ship a second
virtualization daemon. Package and sandbox integration acceptance must pass before
tagging. See [publishing](../release/publishing.md).

The [Windows profile record](../research/windows-guests/README.md) separates
deterministic configuration/provisioning coverage from real Windows installation
and driver acceptance. Windows disk/TPM-state migration is outside these profiles.

## Milestones and dependencies

Deliver working slices in order. Each milestone ends with a runnable demo and its
tests; elapsed dates depend on the M0 results and developer availability.

| Milestone | Deliverables | Exit evidence |
| --- | --- | --- |
| **Scaffold — complete** | Native build, read-only asynchronous bulk discovery, virtualized list, refresh, test driver tests, docs | Builds and deterministic checks pass; creation/control/display remain unimplemented |
| **M0 — prove the foundation** | Record baseline, 0/100/1,000-domain fixtures, KVM/capability diagnostics; GTK 4 console spike on real QEMU | Repeatable measurements; console decision record covering transport, input, audio, resize, release-grab, reconnect, Wayland and dependencies |
| **M1 — manage existing VMs** | Persistent connection, event loop, stable model, search, lifecycle controls, explicit system connection, reconnect | Two clients change the same guest; UI converges without polling; disconnect and shutdown races tested |
| **M2 — create and import** | Wizard, libosinfo defaults, storage allocation, escaped XML, ISO boot, standalone qcow2 import, rollback | Fresh Linux installation and imported Linux guest boot on real KVM; cancelled/failed creation leaves no orphan volume/domain |
| **M3 — daily workflow** | Chosen console path, basic stopped-guest settings, ISO eject, safe remove, keyboard shortcuts | Install → reboot from disk → reopen console → shutdown → remove completes; existing external disks remain intact |
| **M4 — release gates** | Profiling, error polish, translations setup, metadata, DEB/RPM/Flatpak, COPR CLI publishing, user guide | Correctness, performance and package gates pass; signed-off demo and documented limitations; `0.1.0` tag |

M0 precedes M1 and M2. Its console decision determines M2's graphics device.
M2 builds on M1's serialized command service. M3 integrates those workflows; M4
starts only after they work end to end. Do not ship a VM creator without a usable
console path.

## Console decision gate

The current implementation uses SPICE GLib transport with Pirwa's GTK 4 rendering
and libadwaita chrome. It reuses existing SPICE definitions and does not load GTK 3.
The native console replaces the original external-viewer fallback for SPICE;
VNC retains that fallback. See the [decision record](console-decision.md) for
socket ownership, frame-copy costs, supported input/audio and remaining gates.

Synthetic frame profiling and bounded sparse updates are recorded in the
[renderer measurements](../research/display-performance/README.md).
The [active guest profile](../research/active-console-performance/README.md)
adds 1080p/4K controlled GNOME workloads and an explicit dense-frame tail-cost
follow-up. Sparse updates benefit; dense 4K and physical presentation remain open.
The [dense-console follow-up](../research/dense-console-performance/README.md)
adds a measured packed-frame copy optimization and a 12-trial real-console
comparison with a 3072 MiB guest. Dense GTK paint p95 improves modestly, while
the [rounding and memory follow-up](../research/renderer-memory/README.md)
adds bounded texture-lifetime checks and a measured direct rounded-clip path.
Renderer-only trials do not replace the real-console comparison. Detailed GPU
completion/presentation traces and broader guest validation remain open.
The explicit profilers now capture GDK compositor feedback separately from
paint spans, with missing/pending/discarded results retained. Virtual-output
feedback remains separate from physical-presentation acceptance, and the guest
runner requires memory headroom before allocating its disposable fixture.
This is not physical-presentation acceptance.
Acceptance still requires a broader Wayland and physical input/audio matrix,
broader active-application profiling, accelerated-display handling and accessibility review.
The virtual GNOME run is development evidence, not the complete release matrix.

## Performance requirements

[Performance budgets and methodology](performance.md) are release acceptance
criteria. They are provisional targets, not measured claims. Tune architecture
before adding optional features if budgets fail. Keep guest hardware and storage
settings explicit; do not force unsafe cache modes to improve benchmark numbers.

## Correctness and release checklist

- Deterministic test-driver coverage for inventory, commands, lifecycle events,
  reconnect, cancellation, duplicate names, missing domains, and stale completions.
- Fixture tests for XML, validation, ownership, backing-chain rejection, and
  storage rollback, with no real-host mutations in the default test command.
- Disposable real-KVM integration runs for creation, UEFI, networking, viewer,
  shutdown, permission failures, and install-media eject. These require an explicit
  opt-in and isolated resources; the test driver does not emulate QEMU fully.
- Run address/undefined sanitizers and leak checks for lifecycle and close races.
- Verify 200% text scale, keyboard-only navigation, accessible action labels,
  light/dark themes, and a narrow window without clipped controls.
- Publish benchmark inputs, raw samples, environment, comparison method, and
  known limits. Select a controlled application ID, add AppStream metadata and
  CI, choose supported distribution versions, then create the release tag.

The next release work is the remaining acceptance matrix in the implementation
validation record, followed by distribution identity/metadata and release sign-off.
The [metadata follow-up](../research/release-metadata/README.md) now establishes
the owned `io.github.stonega.Pirwa` identity, preserves pre-release preference
storage, and prepares strict offline metadata checks and a real screenshot.
Public asset reachability, committed-candidate CI and stable promotion remain open.
The [backend recovery checks](../research/backend-recovery/README.md) now cover
deterministic transport/permission faults and shutdown during blocked inventory;
the private empty-session daemon now has graceful/crash restart and socket-denial
coverage. Private socket activation through the default Session URI also has
cold-connect, restart and cleanup coverage. A running Linux guest now has synced
ext4/qcow2 write-continuity, process continuity, recovered controls, clean offline
checks and reboot-persistence coverage across daemon replacement. Installed
systemd units, system authorization, broader guest/storage combinations and
backend-stall traces remain separate gates.
