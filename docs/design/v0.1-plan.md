# Pirwa v0.1 plan

## Product outcome

A GNOME desktop user can discover local VMs, create a Linux VM from a local ISO,
install and use it through a console, control its power, change basic resources
while stopped, and remove it safely. Keep the short, approachable workflow of
Boxes. Prioritize responsiveness, idle cost, and guest execution over feature
count. This is a new application, not a Boxes fork.

## Release scope

| Area | v0.1 behavior |
| --- | --- |
| Host | Linux x86_64 with KVM; Fedora is the initial validation platform |
| Connections | `qemu:///session` default; explicitly selected `qemu:///system`; one active connection |
| Collection | Names, states, search, incremental updates, useful empty/error states |
| Power | Start, graceful shutdown, restart, pause/resume; force stop requires explicit confirmation |
| Creation | Local bootable Linux ISO, name, CPU, RAM, disk size, visible progress and rollback |
| Storage | App-created qcow2 volume in a selected writable libvirt pool |
| Guest defaults | KVM, capability-checked host CPU, virtio devices, supported UEFI, available userspace networking |
| Existing VMs | Discover in place without changing XML; import one standalone qcow2 image by copying into an owned volume |
| Console | Working keyboard, mouse, resize/fullscreen; embedded only after M0 passes; supported external viewer otherwise |
| Settings | Rename, CPU and RAM while powered off; ISO eject after install |
| Removal | Remove definition; offer disk deletion only for verified app-owned volumes |
| Integration | Desktop launcher, icon, keyboard access, gettext infrastructure, light/dark and accessibility checks |

Existing qcow2 images with backing chains and unsupported formats must get a
clear rejection in v0.1. Do not modify a user's original image. System mode needs
permission checks; connecting must not automatically create a host-wide network.
Choose available userspace networking from capabilities for session guests.

Snapshots, cloning, unattended installation, ISO downloads, Windows guest support,
USB/GPU passthrough, shared folders, remote hosts, migration, multi-monitor,
background autostart management, and Flatpak distribution are deferred.

## Milestones and dependencies

Deliver working slices in order. Each milestone ends with a runnable demo and its
tests; elapsed dates depend on the M0 results and developer availability.

| Milestone | Deliverables | Exit evidence |
| --- | --- | --- |
| **Scaffold — complete** | Native build, read-only asynchronous bulk discovery, virtualized list, refresh, test driver tests, docs | Builds and deterministic checks pass; creation/control/display remain unimplemented |
| **M0 — prove the foundation** | Record baseline, 0/100/1,000-domain fixtures, KVM/capability diagnostics; GTK 4 console spike on real QEMU | Repeatable measurements; console decision record covering transport, input, audio, resize, release-grab, reconnect, Wayland and dependencies |
| **M1 — manage existing VMs** | Persistent connection, event loop, stable model, search, lifecycle controls, explicit system connection, reconnect | Two clients change the same guest; UI converges without polling; disconnect and shutdown races tested |
| **M2 — create and import** | Wizard, libosinfo defaults, storage allocation, escaped XML, ISO boot, standalone qcow2 import, rollback | Fresh Linux installation and imported Linux guest boot on real KVM; cancelled/failed creation leaves no orphan volume/domain |
| **M3 — daily workflow** | Chosen console path, basic stopped-guest settings, ISO eject, safe remove, keyboard shortcuts | Install → reboot from disk → reopen console → shutdown → remove completes; existing external disks remain intact |
| **M4 — release gates** | Profiling, error polish, translations setup, metadata, native package, user guide | Correctness and performance gates pass; signed-off demo and documented limitations; `0.1.0` tag |

M0 precedes M1 and M2. Its console decision determines M2's graphics device.
M2 builds on M1's serialized command service. M3 integrates those workflows; M4
starts only after they work end to end. Do not ship a VM creator without a usable
console path.

## Console decision gate

The reviewed Boxes source uses `spice-client-gtk-3.0`, which is a GTK 3 widget.
Do not embed it in a GTK 4 process. Investigate libmks and QEMU's D-Bus display as
the native route. Current libmks documentation labels its API `1.0.alpha`, so
verify packaged availability and stability rather than treating it as settled.

Cap the spike at three developer days. Pass only with reproducible libvirt-managed
connection, Wayland input capture/release, resize, fullscreen, reconnect, an
acceptable CPU/frame profile, and an acceptable audio path. Pin the tested
dependency versions and supported host matrix in a decision record. If this
fails, v0.1 opens a supported external libvirt-aware viewer for SPICE/VNC guests.
Launch with argument arrays, pass URI and UUID, and report missing dependencies.
Embedding then moves to a later version; this is an explicit UX compromise.

Sources: [Boxes display dependencies](https://github.com/GNOME/gnome-boxes/blob/78cd19e85b70e796aa17ca26fde611e9bd31608a/src/meson.build),
[libmks API](https://gnome.pages.gitlab.gnome.org/libmks/libmks1/),
[QEMU D-Bus display](https://www.qemu.org/docs/master/interop/dbus-display.html).

## Performance requirements

[Performance budgets and methodology](performance.md) are release acceptance
criteria. They are provisional targets, not measured claims. Tune architecture
before adding optional features if budgets fail. Keep guest hardware and storage
settings explicit; do not force unsafe cache modes to improve benchmark numbers.

## Correctness and release checklist

- Deterministic test-driver coverage for inventory, commands, lifecycle events,
  reconnect, cancellation, duplicate names, missing domains, and stale completions.
- Fixture tests for XML, validation, ownership, backing-chain rejection, and
  storage rollback, with no real-host mutations in the default test command.
- Disposable real-KVM integration runs for creation, UEFI, networking, viewer,
  shutdown, permission failures, and install-media eject. These require an explicit
  opt-in and isolated resources; the test driver does not emulate QEMU fully.
- Run address/undefined sanitizers and leak checks for lifecycle and close races.
- Verify 200% text scale, keyboard-only navigation, accessible action labels,
  light/dark themes, and a narrow window without clipped controls.
- Publish benchmark inputs, raw samples, environment, comparison method, and
  known limits. Select a controlled application ID, add AppStream metadata and
  CI, choose supported distribution versions, then create the release tag.

The immediate next task is **M0**, starting with the display feasibility spike
and bulk inventory baseline, before adding power controls or the creation wizard.
